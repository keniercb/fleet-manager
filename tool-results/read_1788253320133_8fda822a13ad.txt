    31→    31→## 1. Introducción
    32→    32→
    33→    33→El **Sistema de Gestión del Parque de Vehículos** (Fleet Management) es una aplicación backend construida con Spring Boot que proporciona una API REST para la gestión integral de vehículos, choferes, empresas, recorridos, tarjetas de combustible y los catálogos maestros asociados (marcas, tipos de vehículos, tipos de combustible, categorías de licencia, monedas). El sistema implementa control de acceso basado en roles (RBAC) con tres niveles (SUPER_ADMIN, ADMIN, USER), auditoría automática de entidades, lógica de negocio transaccional para la gestión de recorridos y consumo de combustible, y un módulo de reportes de movimiento mensual.
    34→    34→
    35→    35→El sistema está diseñado como un microservicio backend que puede ser consumido por cualquier frontend (Angular, React, Vue) a través de su API REST documentada con OpenAPI/Swagger.
    36→    36→
    37→    37→### Alcance Funcional
    38→    38→
    39→    39→- Gestión de **Empresas** propietarias de vehículos
    40→    40→- Gestión de **Vehículos** con control de odómetro y combustible
    41→    41→- Gestión de **Choferes** con categorías de licencia
    42→    42→- Registro y control de **Recorridos** con cálculo automático de consumo y validación de saldo de tarjetas de combustible
    43→    43→- Gestión de **Tarjetas de Combustible** con control de saldo y relación a monedas
    44→    44→- Gestión de **Monedas (Currency)** como catálogo maestro
    45→    45→- **Reporte de movimiento mensual** por vehículo con análisis de consumo comparado con la norma
    46→    46→- Gestión de catálogos maestros: **Marcas**, **Tipos de Vehículo**, **Tipos de Combustible**, **Categorías de Licencia**
    47→    47→- Sistema de **Autenticación JWT** con tres roles y permisos granulares
    48→    48→- **Auditoría automática** en todas las entidades (creador, modificador, timestamps)
    49→    49→- **Baja lógica** (soft delete) en todas las entidades
    50→    50→- **Filtrado** en endpoints de listado por texto libre
    51→    51→- Cambio de **contraseña** autenticado
    52→    52→- Asociación de **usuarios a empresas** con protección de empresa del administrador

    83→    83→## 3. Arquitectura del Sistema
    84→    84→
    85→    85→### 3.1 Patrón Arquitectónico
    86→    86→
    87→    87→El sistema sigue una **arquitectura en capas (Layered Architecture)** clásica con separación estricta de responsabilidades:
    88→    88→
    89→    89→```
    90→    90→┌──────────────────────────────────────────────┐
    91→    91→│              Cliente (Frontend)              │
    92→    92→│         Angular / React / Vue / cURL         │
    93→    93→└────────────────────┬─────────────────────────┘
    94→    94→                     │ HTTP/REST (JSON)
    95→    95→┌────────────────────▼─────────────────────────┐
    96→    96→│           Controladores (Controllers)         │
    97→    97→│      Validación de entrada, paginación,       │
    98→    98→│      filtrado, mapeo request → servicio      │
    99→    99→├──────────────────────────────────────────────┤
   100→   100→│             Servicios (Services)              │
   101→   101→│      Lógica de negocio, reglas,              │
   102→   102→│      mapeo entidad ↔ DTO                      │
   103→   103→├──────────────────────────────────────────────┤
   104→   104→│            Repositorios (Repositories)        │
   105→   105→│      Spring Data JPA, consultas,             │
   106→   106→│      abstracción de acceso a datos            │
   107→   107→├──────────────────────────────────────────────┤
   108→   108→│              Modelo de Dominio                 │
   109→   109→│      Entidades JPA, BaseEntity,              │
   110→   110→│      relaciones, auditoría                    │
   111→   111→├──────────────────────────────────────────────┤
   112→   112→│               Base de Datos                   │
   113→   113→│        H2 (dev) / PostgreSQL (prod)           │
   114→   114→└──────────────────────────────────────────────┘
   115→   115→```
   116→   116→
   117→   117→### 3.2 Capas Detalladas
   118→   118→
   119→   119→#### Controladores (`controller/`)
   120→   120→
   121→   121→- Exponen endpoints REST bajo el prefijo `/api/`
   122→   122→- Reciben `XRequest` DTOs con anotaciones de validación Jakarta
   123→   123→- Delegan al servicio correspondiente
   124→   124→- Retornan `ResponseEntity<XResponse>` con códigos HTTP apropiados
   125→   125→- Todos los endpoints de listado soportan **paginación** y algunos soportan **filtrado** por texto libre
   126→   126→- 15 controladores REST en total
   127→   127→
   128→   128→#### Servicios (`service/` + `service/impl/`)
   129→   129→
   130→   130→- Cada dominio tiene una interfaz `XService` y su implementación `XServiceImpl`
   131→   131→- 16 servicios en total (incluyendo `AuthService`)
   132→   132→- Contienen toda la lógica de negocio y reglas de validación
   133→   133→- Realizan el mapeo manual entre entidades y DTOs mediante métodos `toResponse()` privados
   134→   134→- Anotados con `@Transactional` para garantizar atomicidad
   135→   135→
   136→   136→#### Repositorios (`repository/`)
   137→   137→
   138→   138→- 14 interfaces Spring Data JPA que extienden `JpaRepository<Entity, Long>`
   139→   139→- Proveen métodos de búsqueda por claves naturales (`findByCodigo`, `findByEmail`, `findByMatricula`, `findByNumero`, `findByIsoCode`, etc.)
   140→   140→- Todos incluyen `findAllByActivoTrue(Pageable)` para soportar baja lógica con paginación
   141→   141→- Algunos incluyen métodos de búsqueda con filtro: `findAllByActivoTrueAndNombreContainingIgnoreCase(String filter, Pageable)`
   142→   142→- Algunos incluyen consultas personalizadas con `@Query`
   143→   143→
   144→   144→#### Modelo (`model/`)
   145→   145→
   146→   146→- 16 entidades JPA que heredan de `BaseEntity`
   147→   147→- Relaciones mapeadas con `FetchType.LAZY` (excepto `User.roles` y `Role.permissions` que son `EAGER`)
   148→   148→- Validaciones con anotaciones Jakarta (`@NotNull`, `@NotBlank`, `@Size`, `@Past`, `@PastOrPresent`, `@DecimalMin`, `@Positive`, `@Email`)

   231→   231→## 5. Modelo de Datos
   232→   232→
   233→   233→### 5.1 BaseEntity — Superclase Abstracta
   234→   234→
   235→   235→Todas las entidades heredan de `BaseEntity`, la cual proporciona campos comunes de identificación, auditoría y eliminación lógica:
   236→   236→
   237→   237→| Campo | Tipo | Restricciones | Descripción |
   238→   238→|---|---|---|---|
   239→   239→| `id` | `Long` | PK, auto-increment `IDENTITY` | Identificador único |
   240→   240→| `activo` | `Boolean` | `NOT NULL`, default `true` | Flag de baja lógica (soft delete) |
   241→   241→| `fechaCreacion` | `LocalDateTime` | `NOT NULL`, `updatable=false` | Fecha de creación (auto vía `@PrePersist`) |
   242→   242→| `fechaActualizacion` | `LocalDateTime` | nullable | Fecha de última modificación (auto vía `@PreUpdate`) |
   243→   243→| `creadoPor` | `User` (lazy) | FK `creado_por_id` | Usuario que creó la entidad |
   244→   244→| `modificadoPor` | `User` (lazy) | FK `modificado_por_id` | Usuario que modificó la entidad por última vez |
   245→   245→
   246→   246→**Mecanismo de auditoría:** Los campos `creadoPor` y `modificadoPor` se pueblan automáticamente en los callbacks `@PrePersist` y `@PreUpdate` de `BaseEntity`, leyendo el `AuthenticatedUser` del `SecurityContextHolder`. Esto permite capturar la entidad `User` completa (no solo el nombre) como referencia de auditoría.

   310→   310→│ consumo       │  └────────┬──────────┘     │    │

   318→   318→└───────────────┘  │ descripcion       │     │    │
   319→   319→                   │ [audit...]        │     │    │
   320→   320→                   └──────────────────┘     │    │
   321→   321→                                             │    │
   322→   322→       Vehiculo ──┬── empresa (FK, NOT NULL)  │

   325→   325→                  ├── chofer (FK, nullable)             │

   327→   327→
   328→   328→┌───────────────────┐     ┌───────────────┐
   329→   329→│ TarjetaCombustible│     │   Currency     │

   331→   331→│ id                │     │ id            │
   332→   332→│ numero (UQ)       │────▶│ isoCode (UQ)  │
   333→   333→│ saldo             │ N:1 │ descripcion   │

   635→   635→## 7. Seguridad y Autenticación
   636→   636→
   637→   637→### 7.1 Flujo de Autenticación JWT
   638→   638→
   639→   639→```
   640→   640→1. Cliente → POST /api/auth/login { email, password }
   641→   641→2. AuthenticationManager → authenticate(username, password)
   642→   642→3. JwtService → generateToken(user)
   643→   643→   - subject: email del usuario
   644→   644→   - claim "roles": lista de nombres de roles
   645→   645→   - expiración: 24 horas
   646→   646→   - algoritmo: HMAC-SHA
   647→   647→4. Respuesta → { token: "eyJhbG..." }
   648→   648→5. Cliente → GET /api/vehiculos con Header: Authorization: Bearer eyJhbG...
   649→   649→6. JwtAuthenticationFilter → extrae token → valida → carga AuthenticatedUser
   650→   650→7. AuthenticatedUser envuelve la entidad User de JPA
   651→   651→8. SecurityContext populated → Authorized
   652→   652→```
   653→   653→
   654→   654→### 7.2 Componentes de Seguridad
   655→   655→
   656→   656→| Componente | Responsabilidad |
   657→   657→|---|---|
   658→   658→| `SecurityConfig` | Configura la cadena de filtros, CORS, reglas de acceso por rol. Usa `@EnableMethodSecurity` para autorización a nivel de método |
   659→   659→| `JwtAuthenticationFilter` | `OncePerRequestFilter` que extrae y valida el token Bearer en cada petición |
   660→   660→| `JwtService` | Genera tokens JWT con claims de roles; valida firma, expiración y sujeto |
   661→   661→| `AuthenticatedUser` | Implementa `UserDetails` envolviendo la entidad `User` de JPA, permitiendo acceso a la entidad completa desde el `SecurityContext` |
   662→   662→| `CustomUserDetailsService` | Carga el usuario desde la base de datos, asignando autoridades `ROLE_` + permisos. Verifica que el usuario esté activo |
   663→   663→
   664→   664→### 7.3 Reglas de Acceso
   665→   665→
   666→   666→| Ruta | Acceso |
   667→   667→|---|---|
   668→   668→| `/api/auth/**` | Público (sin autenticación) |
   669→   669→| `/api/users/**` | Requiere rol `SUPER_ADMIN` o `ADMIN` |
   670→   670→| `/api/roles/**` (GET) | Requiere rol `SUPER_ADMIN` o `ADMIN` |
   671→   671→| `/api/roles/**` (POST/PUT/DELETE) | Requiere rol `SUPER_ADMIN` |
   672→   672→| `/api/permissions/**` | Requiere rol `SUPER_ADMIN` |
   673→   673→| `/swagger-ui/**`, `/v3/api-docs/**` | Público |
   674→   674→| `/h2-console/**` | Público (solo desarrollo) |
   675→   675→| Cualquier otra ruta `/api/**` | Requiere autenticación (cualquier rol) |
   676→   676→
   677→   677→### 7.4 Configuración CORS
   678→   678→
   679→   679→| Propiedad | Valor |
   680→   680→|---|---|
   681→   681→| Orígenes permitidos | `http://localhost:4200`, `http://localhost:3000`, `http://localhost:5173` |
   682→   682→| Métodos permitidos | GET, POST, PUT, PATCH, DELETE, OPTIONS |
   683→   683→| Headers permitidos | `*` (todos) |
   684→   684→| Credenciales | Permitidas |
   685→   685→| Max-Age | 3600 segundos |
   686→   686→
   687→   687→### 7.5 Autoridades Granted
   688→   688→
   689→   689→El `CustomUserDetailsService` asigna dos tipos de autoridades al autenticar un usuario:
   690→   690→
   691→   691→1. **Autoridades de rol:** `ROLE_SUPER_ADMIN`, `ROLE_ADMIN`, `ROLE_USER` (por cada rol asignado al usuario)
   692→   692→2. **Autoridades de permiso:** `vehiculo:read`, `vehiculo:write`, etc. (por cada permiso en cada rol)
   693→   693→
   694→   694→Esto permite el uso de `@PreAuthorize("hasRole('SUPER_ADMIN')")` o `@PreAuthorize("hasAuthority('vehiculo:write')")` en futuros endpoints granulares.

   698→   698→## 8. Capa de Servicios — Lógica de Negocio
   699→   699→
   700→   700→### 8.1 Patrón CRUD Estándar
   701→   701→
   702→   702→Todos los servicios implementan el siguiente patrón, con variaciones específicas por dominio:
   703→   703→
   704→   704→| Operación | Comportamiento general |
   705→   705→|---|---|
   706→   706→| `findAll(Pageable)` | `repository.findAllByActivoTrue(pageable)` → mapea a `Page<XResponse>` |
   707→   707→| `findAll(String filter, Pageable)` | Búsqueda con filtro opcional por texto libre (nombre/código) |
   708→   708→| `findById(Long)` | Busca por ID, lanza `ResourceNotFoundException` si no existe o está inactivo |
   709→   709→| `create(XRequest)` | Valida campos únicos, lanza `BusinessException` si hay duplicados, guarda y retorna respuesta |
   710→   710→| `update(Long, XRequest)` | Valida campos únicos excluyendo la entidad actual, actualiza y retorna respuesta |
   711→   711→| `delete(Long)` | Baja lógica: establece `activo = false` y guarda |
   712→   712→
   713→   713→### 8.2 Lógica de Negocio Específica por Servicio
   714→   714→
   715→   715→#### 8.2.1 RecorridoServiceImpl — La lógica más compleja
   716→   716→
   717→   717→El servicio de recorridos es el núcleo del dominio de negocio y contiene las reglas transaccionales más críticas del sistema:
   718→   718→
   719→   719→**Creación de recorrido (`create`):**
   720→   720→1. Valida que el vehículo exista
   721→   721→2. Verifica unicidad: no puede existir más de un recorrido para el mismo vehículo en la misma fecha
   722→   722→3. Verifica orden cronológico: no se puede insertar un recorrido con fecha anterior si ya existe un recorrido posterior para el mismo vehículo
   723→   723→4. Registra el `combustibleInicial` como el combustible actual del vehículo
   724→   724→5. Calcula automáticamente el consumo: `consumo = (índiceConsumo × kilómetros) / 100`, redondeado a 2 decimales
   725→   725→6. Valida disponibilidad de combustible: `combustibleRestante = combustibleActual - consumo + litrosAbastecidos >= 0`
   726→   726→7. Registra el `odometroInicial` como el odómetro actual del vehículo
   727→   727→8. Si se usa tarjeta de combustible, valida que el `importeAbastecido` no exceda el saldo disponible y descuenta del saldo
   728→   728→9. Actualiza atómicamente el vehículo: incrementa el odómetro y decrementa el combustible
   729→   729→10. Todas las operaciones se ejecutan dentro de una transacción `@Transactional`
   730→   730→
   731→   731→**Actualización de recorrido (`update`):**
   732→   732→1. No permite cambiar el vehículo ni la fecha del recorrido
   733→   733→2. Restaura el consumo antiguo al vehículo antes de calcular el nuevo
   734→   734→3. Restaura el combustible inicial y el saldo de la tarjeta (si aplica)
   735→   735→4. Recalcula el consumo con los nuevos kilómetros
   736→   736→5. Verifica disponibilidad de combustible y saldo de tarjeta con los nuevos valores
   737→   737→6. Restaura y recalcula el odómetro del vehículo
   738→   738→7. Actualiza atómicamente la entidad y el vehículo
   739→   739→
   740→   740→**Eliminación de recorrido (`delete`):**
   741→   741→1. Restaura los kilómetros al odómetro del vehículo (resta)
   742→   742→2. Restaura el combustible consumido al vehículo (suma)
   743→   743→3. Restaura el saldo de la tarjeta de combustible (si aplica)
   744→   744→4. Ejecuta la baja lógica del recorrido (`activo = false`)
   745→   745→
   746→   746→#### 8.2.2 ChoferServiceImpl — Creación anidada de categorías
   747→   747→
   748→   748→- El `ChoferRequest` incluye una lista de `CategoriaConFechaRequest` (pares `categoriaLicenciaId` + `fechaEmision`)
   749→   749→- Al crear un chofer, se crean automáticamente las relaciones `ChoferCategoria` con sus fechas de emisión
   750→   750→- Al actualizar, se eliminan todas las categorías existentes y se recrean con la nueva lista
   751→   751→- Al eliminar, se desactivan también todas las categorías del chofer
   752→   752→
   753→   753→#### 8.2.3 VehiculoServiceImpl — Validación de doble unicidad
   754→   754→
   755→   755→- Valida que tanto la `matrícula` como el `número de motor` sean únicos al crear y actualizar
   756→   756→- Al actualizar, excluye el ID del vehículo actual de la verificación de unicidad
   757→   757→- Delega al servicio de recorridos la generación del reporte mensual de movimiento
   758→   758→
   759→   759→#### 8.2.4 TarjetaCombustibleServiceImpl — Control de saldo
   760→   760→
   761→   761→- Al crear una tarjeta, el saldo inicial debe ser positivo
   762→   762→- La validación de saldo en recorridos se realiza en `RecorridoServiceImpl`, no aquí
   763→   763→- Soporta filtrado por empresa y búsqueda por número
   764→   764→
   765→   765→#### 8.2.5 AuthServiceImpl — Autenticación y cambio de contraseña
   766→   766→
   767→   767→- `login`: Autentica vía `AuthenticationManager`, genera token JWT, retorna `AuthResponseDto` con token, email, roles y permisos
   768→   768→- `getCurrentUser`: Retorna la entidad `User` del `SecurityContext`
   769→   769→- `cambiarPassword`: Valida contraseña anterior, verifica coincidencia de nueva contraseña y confirmación, encripta y guarda
   770→   770→
   771→   771→### 8.3 Mapeo Entidad ↔ DTO
   772→   772→
   773→   773→El mapeo se realiza de forma **manual** en cada `XServiceImpl` mediante métodos privados `toResponse()` y `toEntity()` o `toResumido()`. No se utiliza MapStruct ni ninguna librería de mapeo automático.
   774→   774→
   775→   775→**Patrón típico:**
   776→   776→
   777→   777→```java
   778→   778→private XResponse toResponse(X entity) {
   779→   779→    return XResponse.builder()
   780→   780→            .id(entity.getId())
   781→   781→            .campo1(entity.getCampo1())
   782→   782→            .campo2(entity.getCampo2())
   783→   783→            .activo(entity.getActivo())
   784→   784→            .fechaCreacion(entity.getFechaCreacion())
   785→   785→            .fechaActualizacion(entity.getFechaActualizacion())
   786→   786→            .creadoPor(AuditMapper.toAuditResponse(entity.getCreadoPor()))
   787→   787→            .modificadoPor(AuditMapper.toAuditResponse(entity.getModificadoPor()))
   788→   788→            .build();
   789→   789→}
   790→   790→```
   791→   791→
   792→   792→**Para relaciones anidadas**, se crean métodos auxiliares como `toEmpresaResumido()` que construyen respuestas parciales para evitar referencias circulares.

   796→   796→## 9. Reportes
   797→   797→
   798→   798→### 9.1 Reporte de Movimiento Mensual por Vehículo
   799→   799→
   800→   800→**Endpoint:** `GET /api/vehiculos/reporte-movimiento-mensual/{vehiculoId}?mes={mes}&anio={anio}`
   801→   801→
   802→   802→Este reporte genera un análisis completo del consumo de combustible de un vehículo durante un mes específico. Se calcula de forma iterativa día a día simulando el estado del depósito de combustible y el odómetro.
   803→   803→
   804→   804→**Parámetros:**
   805→   805→
   806→   806→| Parámetro | Tipo | Descripción |
   807→   807→|---|---|---|
   808→   808→| `vehiculoId` | Long (path) | ID del vehículo |
   809→   809→| `mes` | Integer (query) | Mes (1-12) |
   810→   810→| `anio` | Integer (query) | Año (ej: 2026) |
   811→   811→
   812→   812→**Respuesta (`ReporteMovimientoMensualResponse`):**
   813→   813→
   814→   814→```json
   815→   815→{
   816→   816→  "vehiculo": {
   817→   817→    "marca": "Toyota",
   818→   818→    "numeroMotor": "ABC123",
   819→   819→    "tipoCombustible": "Diesel",
   820→   820→    "normaConsumo": 8.50,
   821→   821→    "matricula": "A-123-456",
   822→   822→    "chofer": { ... }
   823→   823→  },
   824→   824→  "lecturas": [
   825→   825→    {
   826→   826→      "dia": 1,
   827→   827→      "odometro": 15000,
   828→   828→      "combustibleEnDeposito": 50.00,
   829→   829→      "combustibleConsumido": 8.50,
   830→   830→      "combustibleAbastecido": 0.00,
   831→   831→      "saldoCombustible": 41.50,
   832→   832→      "kilometrosRecorridos": 100
   833→   833→    }
   834→   834→  ],
   835→   835→  "analisis": {
   836→   836→    "combustibleInicial": 50.00,
   837→   837→    "combustibleRecibido": 20.00,
   838→   838→    "combustibleConsumido": 45.50,
   839→   839→    "existenciaFinal": 24.50,
   840→   840→    "kilometrosRecorridos": 535,
   841→   841→    "consumidoSegunNorma": 45.48
   842→   842→  }
   843→   843→}
   844→   844→```
   845→   845→
   846→   846→**DTOs del reporte:**
   847→   847→
   848→   848→| DTO | Campos | Descripción |
   849→   849→|---|---|---|
   850→   850→| `VehiculoReporteData` | `marca`, `numeroMotor`, `tipoCombustible`, `normaConsumo`, `matricula`, `chofer` | Datos del vehículo para el encabezado del reporte |
   851→   851→| `LecturaDiariaResponse` | `dia`, `odometro`, `combustibleEnDeposito`, `combustibleConsumido`, `combustibleAbastecido`, `saldoCombustible`, `kilometrosRecorridos` | Estado diario simulado del depósito |
   852→   852→| `AnalisisConsumoResponse` | `combustibleInicial`, `combustibleRecibido`, `combustibleConsumido`, `existenciaFinal`, `kilometrosRecorridos`, `consumidoSegunNorma` | Resumen mensual con comparación contra la norma |
   853→   853→
   854→   854→**Lógica de cálculo:**
   855→   855→
   856→   856→El reporte procesa los recorridos del vehículo ordenados por fecha dentro del mes solicitado. Para cada día del mes, se calcula:
   857→   857→- Si hay recorrido ese día: se registra el consumo real, los kilómetros recorridos y el abastecimiento
   858→   858→- Si no hay recorrido: se copian los valores del día anterior (odómetro y combustible se mantienen)
   859→   859→- El `saldoCombustible` se calcula como: `combustibleEnDeposito - combustibleConsumido + combustibleAbastecido`
   860→   860→- El análisis final compara el consumo real total con el consumo esperado según la norma (índiceConsumo)

  1005→  1005→## 13. Decisiones de Diseño
  1006→  1006→
  1007→  1007→### 13.1 Baja Lógica (Soft Delete) Universal
  1008→  1008→
  1009→  1009→**Decisión:** Todas las entidades incluyen un campo `activo` (Boolean, default `true`). La eliminación nunca borra registros físicamente; simplemente cambia `activo` a `false`.
  1010→  1010→
  1011→  1011→**Justificación:** En un sistema de gestión de flotas, la integridad histórica de los datos es crítica. Un vehículo dado de baja puede tener recorridos asociados; eliminarlo físicamente destruiría la cadena de auditoría. La baja lógica permite mantener la trazabilidad completa.
  1012→  1012→
  1013→  1013→**Implementación:** Todos los repositorios exponen `findAllByActivoTrue(Pageable)` y los servicios filtran exclusivamente por `activo = true` en las operaciones de lectura.
  1014→  1014→
  1015→  1015→### 13.2 Auditoría Automática vía BaseEntity + SecurityContext
  1016→  1016→
  1017→  1017→**Decisión:** Los campos de auditoría (`creadoPor`, `modificadoPor`, `fechaCreacion`, `fechaActualizacion`) se pueblan automáticamente en los callbacks JPA `@PrePersist` y `@PreUpdate` de `BaseEntity`, leyendo el `AuthenticatedUser` del `SecurityContextHolder`.
  1018→  1018→
  1019→  1019→**Justificación:** A diferencia del enfoque estándar de Spring Data JPA Auditing (`@CreatedBy`, `@LastModifiedBy`), este diseño permite capturar la entidad `User` completa (no solo el username) como referencia de auditoría. Esto habilita mostrar el nombre y email del auditor en las respuestas DTO sin consultas adicionales.
  1020→  1020→
  1021→  1021→**Trade-off:** El `BaseEntity` tiene una dependencia directa al `SecurityContextHolder`, lo que acopla la capa de modelo al contexto de seguridad de Spring. Durante el bootstrap (`DataInitializer`), el `SecurityContext` está vacío, por lo que los campos de auditoría quedan como `null`.
  1022→  1022→
  1023→  1023→### 13.3 AuthenticatedUser envuelve la entidad User
  1024→  1024→
  1025→  1025→**Decisión:** `AuthenticatedUser` implementa `UserDetails` y envuelve la entidad JPA `User` completa en lugar de solo almacenar credenciales.
  1026→  1026→
  1027→  1027→**Justificación:** Necesario para que `BaseEntity.getAuthenticatedUser()` pueda retornar la entidad `User` y asignarla directamente a los campos `creadoPor`/`modificadoPor`. Esto evita una consulta adicional al repositorio en cada operación de auditoría.
  1028→  1028→
  1029→  1029→### 13.4 Mapeo DTO Manual (sin MapStruct)
  1030→  1030→
  1031→  1031→**Decisión:** El mapeo entre entidades y DTOs se realiza manualmente en cada `ServiceImpl`.
  1032→  1032→
  1033→  1033→**Justificación (presumida):** Simplicidad inicial del proyecto, evitar una dependencia adicional.
  1034→  1034→
  1035→  1035→**Trade-off:** Genera duplicación significativa de código. Por ejemplo, `toEmpresaResponse()` está duplicado en múltiples servicios. Una refactorización futura con MapStruct o con mappers compartidos reduciría el código y mejoraría el mantenimiento.
  1036→  1036→
  1037→  1037→### 13.5 Tres Niveles de Roles (SUPER_ADMIN / ADMIN / USER)
  1038→  1038→
  1039→  1039→**Decisión:** Se introdujo un tercer rol `SUPER_ADMIN` con acceso total, diferenciándolo del rol `ADMIN` que no puede gestionar roles ni permisos.
  1040→  1040→
  1041→  1041→**Justificación:** En un sistema multi-empresa, el rol `ADMIN` se reserva para administradores de empresa que no deben poder modificar la estructura de roles y permisos del sistema. Solo el `SUPER_ADMIN` tiene control total sobre la configuración de seguridad.
  1042→  1042→
  1043→  1043→**Implementación:** `SecurityConfig` utiliza reglas diferenciadas: `GET /api/roles/**` permite ambos roles, pero operaciones de escritura requieren `SUPER_ADMIN` exclusivamente.
  1044→  1044→
  1045→  1045→### 13.6 Asociación Usuario-Empresa
  1046→  1046→
  1047→  1047→**Decisión:** Se agregó un campo `empresa` (nullable, LAZY) a la entidad `User`, permitiendo asociar usuarios a empresas.
  1048→  1048→
  1049→  1049→**Justificación:** Necesario para el modelo multi-empresa donde los usuarios (choferes, administradores de empresa) pertenecen a una empresa específica.
  1050→  1050→
  1051→  1051→**Protección:** El `DataInitializer` crea automáticamente la empresa por defecto (`EMP-ADMIN`) y la asigna al usuario administrador. El endpoint `/api/auth/me` retorna la información de la empresa del usuario autenticado.
  1052→  1052→
  1053→  1053→### 13.7 Filtrado por Texto Libre en Endpoints de Listado
  1054→  1054→
  1055→  1055→**Decisión:** Los endpoints de listado principales soportan un parámetro `filter` opcional que permite buscar por texto libre (coincidencia parcial, case-insensitive) en campos de nombre o código.
  1056→  1056→
  1057→  1057→**Justificación:** Mejora significativamente la experiencia del usuario al permitir búsquedas rápidas sin necesidad de endpoints dedicados para cada criterio de búsqueda.
  1058→  1058→
  1059→  1059→### 13.8 Sin Migraciones de Base de Datos (ddl-auto=update)
  1060→  1060→
  1061→  1061→**Decisión:** Se utiliza `spring.jpa.hibernate.ddl-auto=update` para generar y actualizar el esquema automáticamente.
  1062→  1062→
  1063→  1063→**Justificación:** Rapidez en el desarrollo inicial.
  1064→  1064→
  1065→  1065→**Trade-off:** Este enfoque es frágil para cambios de esquema en producción (no genera `ALTER TABLE` para renombrar o eliminar columnas). Para producción, se recomienda migrar a Flyway o Liquibase.
  1066→  1066→
  1067→  1067→### 13.9 Respuestas DTO Anidadas Completas
  1068→  1068→
  1069→  1069→**Decisión:** Los DTOs de respuesta incluyen objetos anidados completos. Por ejemplo, `RecorridoResponse` contiene un `VehiculoResponse` completo, que a su vez contiene `EmpresaResponse`, `MarcaResponse`, etc.
  1070→  1070→
  1071→  1071→**Justificación:** Simplifica el consumo del API para el frontend, evitando múltiples llamadas para obtener datos relacionados.
  1072→  1072→
  1073→  1073→**Trade-off:** Riesgo de problemas de rendimiento por lazy loading (N+1 queries) y respuestas muy grandes. El setting `spring.jpa.open-in-view=false` ayuda a detectar estos problemas en tiempo de desarrollo.
  1074→  1074→
  1075→  1075→### 13.10 Paginación 1-based desde el Cliente
  1076→  1076→
  1077→  1077→**Decisión:** Los controladores exponen parámetros de paginación 1-based (page=1 es la primera página) y `PaginationUtils.params()` convierte internamente a 0-based para Spring Data.
  1078→  1078→
  1079→  1079→**Justificación:** Más intuitivo para los consumidores del API.
  1080→  1080→
  1081→  1081→**Trade-off:** Si el cliente envía `page=0`, `PaginationUtils.params()` lo convierte a `Math.max(0, 0-1) = 0`, lo que es correcto pero podría confundir. La consistencia del API depende de la documentación.
  1082→  1082→
  1083→  1083→### 13.11 Sesiones Stateless con JWT
  1084→  1084→
  1085→  1085→**Decisión:** La configuración de seguridad establece `SessionCreationPolicy.STATELESS` y no se almacena estado de sesión en el servidor.
  1086→  1086→
  1087→  1087→**Justificación:** Facilita la escalabilidad horizontal y es el patrón estándar para APIs REST consumidas por frontends SPA o móviles. El estado se codifica en el propio token JWT.

  1162→  1162→## 16. Problemas Conocidos y Mejoras Pendientes
  1163→  1163→
  1164→  1164→### 16.1 Problemas Conocidos
  1165→  1165→
  1166→  1166→| # | Severidad | Problema | Descripción |
  1167→  1167→|---|---|---|---|
  1168→  1168→| 1 | 🟡 Media | JWT secret hardcoded | La clave JWT está en `application.properties` como texto plano. Debería usarse variable de entorno o vault |
  1169→  1169→| 2 | 🟡 Media | Contraseña admin hardcoded | `admin123` en `DataInitializer.java` es una contraseña por defecto insegura |
  1170→  1170→| 3 | 🟡 Media | Duplicación de mapeo DTO | `toEmpresaResponse()` y otros mappers están duplicados en múltiples servicios |
  1171→  1171→| 4 | 🟠 Baja | Sin migraciones DB | `ddl-auto=update` es frágil para producción; no controla cambios de esquema |
  1172→  1172→| 5 | 🟠 Baja | Riesgo N+1 queries | Respuestas DTO con anidamiento profundo + lazy loading pueden causar problemas de rendimiento |
  1173→  1173→| 6 | 🟠 Baja | Sin caché | Cada llamada al servicio impacta la base de datos sin capa de caché |
  1174→  1174→| 7 | 🟠 Baja | Page 0 API inconsistency | Si el cliente envía `page=0`, la conversión 1→0-based da 0 (funciona pero es confuso) |
  1175→  1175→| 8 | 🟠 Baja | Pruebas faltantes | No existen pruebas para `CurrencyServiceImpl` ni `TarjetaCombustibleServiceImpl` |
  1176→  1176→
  1177→  1177→### 16.2 Mejoras Recomendadas
  1178→  1178→
  1179→  1179→1. **Introducir MapStruct** — Eliminar duplicación de mapeo DTO, generar mappers en tiempo de compilación
  1180→  1180→2. **Externalizar credenciales** — Mover JWT secret y contraseña admin a variables de entorno
  1181→  1181→3. **Adoptar Flyway o Liquibase** — Control versionado del esquema de base de datos para producción
  1182→  1182→4. **Implementar `@EntityGraph` o FETCH JOIN** — Evitar problemas N+1 en respuestas anidadas
  1183→  1183→5. **Crear mappers compartidos** — Como paso intermedio antes de MapStruct, extraer mapeos comunes a clases utilitarias
  1184→  1184→6. **Agregar pruebas de integración** — Al menos para los flujos críticos (recorridos, autenticación)
  1185→  1185→7. **Implementar rate limiting** — Proteger los endpoints de autenticación contra ataques de fuerza bruta
  1186→  1186→8. **Completar cobertura de pruebas** — Agregar tests para `CurrencyServiceImpl` y `TarjetaCombustibleServiceImpl`
  1187→  1187→9. **Generación de reportes PDF** — Implementar exportación a PDF del reporte de movimiento mensual usando Thymeleaf + Flying Saucer (OpenPDF)
  1188→  1188→10. **Sistema de suscripciones/planes** — Implementar modelo de suscripción por empresa con límites de vehículos y planes de facturación
  1189→  1189→11. **Modelo geográfico (Provincia/Municipio)** — Agregar provincias y municipios como catálogos maestros y asociarlos a la entidad Empresa
