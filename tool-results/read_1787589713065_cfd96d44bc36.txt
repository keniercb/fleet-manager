    30→## 1. Introducción
    31→
    32→El **Sistema de Gestión del Parque de Vehículos** (Fleet Management) es una aplicación backend construida con Spring Boot que proporciona una API REST para la gestión integral de vehículos, choferes, empresas, recorridos y los catálogos maestros asociados (marcas, tipos de vehículos, tipos de combustible, categorías de licencia). El sistema implementa control de acceso basado en roles (RBAC), auditoría automática de entidades y lógica de negocio transaccional para la gestión de recorridos y consumo de combustible.
    33→
    34→El sistema está diseñado como un microservicio backend que puede ser consumido por cualquier frontend (Angular, React, Vue) a través de su API REST documentada con OpenAPI/Swagger.
    35→
    36→### Alcance Funcional
    37→
    38→- Gestión de **Empresas** propietarias de vehículos
    39→- Gestión de **Vehículos** con control de odómetro y combustible
    40→- Gestión de **Choferes** con categorías de licencia
    41→- Registro y control de **Recorridos** con cálculo automático de consumo
    42→- Gestión de catálogos maestros: **Marcas**, **Tipos de Vehículo**, **Tipos de Combustible**, **Categorías de Licencia**
    43→- Sistema de **Autenticación JWT** con roles y permisos granulares
    44→- **Auditoría automática** en todas las entidades (creador, modificador, timestamps)
    45→- **Baja lógica** (soft delete) en todas las entidades

    75→## 3. Arquitectura del Sistema
    76→
    77→### 3.1 Patrón Arquitectónico
    78→
    79→El sistema sigue una **arquitectura en capas (Layered Architecture)** clásica con separación estricta de responsabilidades:
    80→
    81→```
    82→┌──────────────────────────────────────────────┐
    83→│              Cliente (Frontend)              │
    84→│         Angular / React / Vue / cURL         │
    85→└────────────────────┬─────────────────────────┘
    86→                     │ HTTP/REST (JSON)
    87→┌────────────────────▼─────────────────────────┐
    88→│           Controladores (Controllers)         │
    89→│      Validación de entrada, paginación,       │
    90→│      mapeo request → servicio                 │
    91→├──────────────────────────────────────────────┤
    92→│             Servicios (Services)              │
    93→│      Lógica de negocio, reglas,              │
    94→│      mapeo entidad ↔ DTO                      │
    95→├──────────────────────────────────────────────┤
    96→│            Repositorios (Repositories)        │
    97→│      Spring Data JPA, consultas,             │
    98→│      abstracción de acceso a datos            │
    99→├──────────────────────────────────────────────┤
   100→│              Modelo de Dominio                 │
   101→│      Entidades JPA, BaseEntity,              │
   102→│      relaciones, auditoría                    │
   103→├──────────────────────────────────────────────┤
   104→│               Base de Datos                   │
   105→│        H2 (dev) / PostgreSQL (prod)           │
   106→└──────────────────────────────────────────────┘
   107→```
   108→
   109→### 3.2 Capas Detalladas
   110→
   111→#### Controladores (`controller/`)
   112→
   113→- Exponen endpoints REST bajo el prefijo `/api/`
   114→- Reciben `XRequest` DTOs con anotaciones de validación Jakarta
   115→- Delegan al servicio correspondiente
   116→- Retornan `ResponseEntity<XResponse>` con códigos HTTP apropiados
   117→- Todos los endpoints de listado soportan paginación con parámetros estándar
   118→
   119→#### Servicios (`service/` + `service/impl/`)
   120→
   121→- Cada dominio tiene una interfaz `XService` y su implementación `XServiceImpl`
   122→- Contienen toda la lógica de negocio y reglas de validación
   123→- Realizan el mapeo manual entre entidades y DTOs mediante métodos `toResponse()` privados
   124→- Anotados con `@Transactional` para garantizar atomicidad
   125→
   126→#### Repositorios (`repository/`)
   127→
   128→- Interfaces Spring Data JPA que extienden `JpaRepository<Entity, Long>`
   129→- Proveen métodos de búsqueda por claves naturales (`findByCodigo`, `findByEmail`, `findByMatricula`, etc.)
   130→- Todos incluyen `findAllByActivoTrue(Pageable)` para soportar baja lógica con paginación
   131→- Algunos incluyen consultas personalizadas con `@Query`
   132→
   133→#### Modelo (`model/`)
   134→
   135→- 13 entidades JPA que heredan de `BaseEntity`
   136→- Relaciones mapeadas con `FetchType.LAZY` (excepto `User.roles` y `Role.permissions` que son `EAGER`)
   137→- Validaciones con anotaciones Jakarta (`@NotNull`, `@NotBlank`, `@Size`, `@Past`, `@DecimalMin`)

   215→## 5. Modelo de Datos
   216→
   217→### 5.1 BaseEntity — Superclase Abstracta
   218→
   219→Todas las entidades heredan de `BaseEntity`, la cual proporciona campos comunes de identificación, auditoría y eliminación lógica:
   220→
   221→| Campo | Tipo | Restricciones | Descripción |
   222→|---|---|---|---|
   223→| `id` | `Long` | PK, auto-increment `IDENTITY` | Identificador único |
   224→| `activo` | `Boolean` | `NOT NULL`, default `true` | Flag de baja lógica (soft delete) |
   225→| `fechaCreacion` | `LocalDateTime` | `NOT NULL`, `updatable=false` | Fecha de creación (auto vía `@PrePersist`) |
   226→| `fechaActualizacion` | `LocalDateTime` | nullable | Fecha de última modificación (auto vía `@PreUpdate`) |
   227→| `creadoPor` | `User` (lazy) | FK `creado_por_id` | Usuario que creó la entidad |
   228→| `modificadoPor` | `User` (lazy) | FK `modificado_por_id` | Usuario que modificó la entidad por última vez |
   229→
   230→**Mecanismo de auditoría:** Los campos `creadoPor` y `modificadoPor` se pueblan automáticamente en los callbacks `@PrePersist` y `@PreUpdate` de `BaseEntity`, leyendo el `AuthenticatedUser` del `SecurityContextHolder`. Esto permite capturar la entidad `User` completa (no solo el nombre) como referencia de auditoría.

   568→## 7. Seguridad y Autenticación
   569→
   570→### 7.1 Flujo de Autenticación JWT
   571→
   572→```
   573→1. Cliente → POST /api/auth/login { email, password }
   574→2. AuthenticationManager → authenticate(username, password)
   575→3. JwtService → generateToken(user)
   576→   - subject: email del usuario
   577→   - claim "roles": lista de nombres de roles
   578→   - expiración: 24 horas
   579→   - algoritmo: HMAC-SHA
   580→4. Respuesta → { token: "eyJhbG..." }
   581→5. Cliente → GET /api/vehiculos con Header: Authorization: Bearer eyJhbG...
   582→6. JwtAuthenticationFilter → extrae token → valida → carga AuthenticatedUser
   583→7. AuthenticatedUser envuelve la entidad User de JPA
   584→8. SecurityContext populated → Authorized
   585→```
   586→
   587→### 7.2 Componentes de Seguridad
   588→
   589→| Componente | Responsabilidad |
   590→|---|---|
   591→| `SecurityConfig` | Configura la cadena de filtros, CORS, reglas de acceso por rol |
   592→| `JwtAuthenticationFilter` | `OncePerRequestFilter` que extrae y valida el token Bearer en cada petición |
   593→| `JwtService` | Genera tokens JWT con claims de roles; valida firma, expiración y sujeto |
   594→| `AuthenticatedUser` | Implementa `UserDetails` envolviendo la entidad `User` de JPA, permitiendo acceso a la entidad completa desde el `SecurityContext` |
   595→| `CustomUserDetailsService` | Carga el usuario desde la base de datos, asignando autoridades `ROLE_` + permisos |
   596→

   620→
   621→El `CustomUserDetailsService` asigna dos tipos de autoridades al autenticar un usuario:

   630→## 8. Capa de Servicios — Lógica de Negocio
   631→
   632→### 8.1 Patrón CRUD Estándar
   633→
   634→Todos los servicios implementan el siguiente patrón, con variaciones específicas por dominio:
   635→
   636→| Operación | Comportamiento general |
   637→|---|---|
   638→| `findAll(Pageable)` | `repository.findAllByActivoTrue(pageable)` → mapea a `Page<XResponse>` |
   639→| `findById(Long)` | Busca por ID, lanza `ResourceNotFoundException` si no existe o está inactivo |
   640→| `create(XRequest)` | Valida campos únicos, lanza `BusinessException` si hay duplicados, guarda y retorna respuesta |
   641→| `update(Long, XRequest)` | Valida campos únicos excluyendo la entidad actual, actualiza y retorna respuesta |
   642→| `delete(Long)` | Baja lógica: establece `activo = false` y guarda |
   643→
   644→### 8.2 Lógica de Negocio Específica por Servicio
   645→
   646→#### 8.2.1 RecorridoServiceImpl — La lógica más compleja
   647→
   648→El servicio de recorridos es el núcleo del dominio de negocio y contiene las reglas transaccionales más críticas del sistema:
   649→
   650→**Creación de recorrido (`create`):**
   651→1. Valida que el vehículo exista
   652→2. Verifica unicidad: no puede existir más de un recorrido para el mismo vehículo en la misma fecha
   653→3. Verifica orden cronológico: no se puede insertar un recorrido con fecha anterior si ya existe un recorrido posterior para el mismo vehículo
   654→4. Calcula automáticamente el consumo: `consumo = (índiceConsumo × kilómetros) / 100`, redondeado a 2 decimales
   655→5. Valida disponibilidad de combustible: `combustibleRestante = combustibleActual - consumo + litrosAbastecidos >= 0`
   656→6. Registra el `odometroInicial` como el odómetro actual del vehículo
   657→7. Actualiza atómicamente el vehículo: incrementa el odómetro y decrementa el combustible
   658→8. Todas las operaciones se ejecutan dentro de una transacción `@Transactional`
   659→
   660→**Actualización de recorrido (`update`):**
   661→1. No permite cambiar el vehículo ni la fecha del recorrido
   662→2. Restaura el consumo antiguo al vehículo antes de calcular el nuevo
   663→3. Recalcula el consumo con los nuevos kilómetros
   664→4. Verifica disponibilidad de combustible con el nuevo consumo
   665→5. Restaura y recalcula el odómetro del vehículo
   666→6. Actualiza atómicamente la entidad y el vehículo
   667→
   668→**Eliminación de recorrido (`delete`):**
   669→1. Restaura los kilómetros al odómetro del vehículo (resta)
   670→2. Restaura el combustible consumido al vehículo (suma)
   671→3. Ejecuta la baja lógica del recorrido (`activo = false`)
   672→
   673→#### 8.2.2 ChoferServiceImpl — Creación anidada de categorías
   674→
   675→- El `ChoferRequest` incluye una lista de `CategoriaConFechaRequest` (pares `categoriaLicenciaId` + `fechaEmision`)
   676→- Al crear un chofer, se crean automáticamente las relaciones `ChoferCategoria` con sus fechas de emisión
   677→- Al actualizar, se eliminan todas las categorías existentes y se recrean con la nueva lista
   678→- Al eliminar, se desactivan también todas las categorías del chofer
   679→
   680→#### 8.2.3 VehiculoServiceImpl — Validación de doble unicidad
   681→
   682→- Valida que tanto la `matrícula` como el `número de motor` sean únicos al crear y actualizar
   683→- Al actualizar, excluye el ID del vehículo actual de la verificación de unicidad
   684→
   685→### 8.3 Mapeo Entidad ↔ DTO
   686→
   687→El mapeo se realiza de forma **manual** en cada `XServiceImpl` mediante métodos privados `toResponse()` y `toEntity()` o `toResumido()`. No se utiliza MapStruct ni ninguna librería de mapeo automático.
   688→
   689→**Patrón típico:**
   690→
   691→```java
   692→private XResponse toResponse(X entity) {
   693→    return XResponse.builder()
   694→            .id(entity.getId())
   695→            .campo1(entity.getCampo1())
   696→            .campo2(entity.getCampo2())
   697→            .activo(entity.getActivo())
   698→            .fechaCreacion(entity.getFechaCreacion())
   699→            .fechaActualizacion(entity.getFechaActualizacion())
   700→            .creadoPor(AuditMapper.toAuditResponse(entity.getCreadoPor()))
   701→            .modificadoPor(AuditMapper.toAuditResponse(entity.getModificadoPor()))
   702→            .build();
   703→}
   704→```
   705→
   706→**Para relaciones anidadas**, se crean métodos auxiliares como `toEmpresaResumido()` que construyen respuestas parciales para evitar referencias circulares.

   714→| Excepción | Código HTTP | Uso |

   719→| `Exception` (catch-all) | 500 Internal Server Error | Errores no esperados |

   722→
   723→```json
   724→{

   727→  "error": "Not Found",

   840→## 12. Decisiones de Diseño
   841→
   842→### 12.1 Baja Lógica (Soft Delete) Universal
   843→
   844→**Decisión:** Todas las entidades incluyen un campo `activo` (Boolean, default `true`). La eliminación nunca borra registros físicamente; simplemente cambia `activo` a `false`.
   845→
   846→**Justificación:** En un sistema de gestión de flotas, la integridad histórica de los datos es crítica. Un vehículo dado de baja puede tener recorridos asociados; eliminarlo físicamente destruiría la cadena de auditoría. La baja lógica permite mantener la trazabilidad completa.
   847→
   848→**Implementación:** Todos los repositorios exponen `findAllByActivoTrue(Pageable)` y los servicios filtran exclusivamente por `activo = true` en las operaciones de lectura.
   849→
   850→### 12.2 Auditoría Automática vía BaseEntity + SecurityContext
   851→
   852→**Decisión:** Los campos de auditoría (`creadoPor`, `modificadoPor`, `fechaCreacion`, `fechaActualizacion`) se pueblan automáticamente en los callbacks JPA `@PrePersist` y `@PreUpdate` de `BaseEntity`, leyendo el `AuthenticatedUser` del `SecurityContextHolder`.
   853→
   854→**Justificación:** A diferencia del enfoque estándar de Spring Data JPA Auditing (`@CreatedBy`, `@LastModifiedBy`), este diseño permite capturar la entidad `User` completa (no solo el username) como referencia de auditoría. Esto habilita mostrar el nombre y email del auditor en las respuestas DTO sin consultas adicionales.
   855→
   856→**Trade-off:** El `BaseEntity` tiene una dependencia directa al `SecurityContextHolder`, lo que acopla la capa de modelo al contexto de seguridad de Spring. Durante el bootstrap (`DataInitializer`), el `SecurityContext` está vacío, por lo que los campos de auditoría quedan como `null`.
   857→
   858→### 12.3 AuthenticatedUser envuelve la entidad User
   859→
   860→**Decisión:** `AuthenticatedUser` implementa `UserDetails` y envuelve la entidad JPA `User` completa en lugar de solo almacenar credenciales.
   861→
   862→**Justificación:** Necesario para que `BaseEntity.getAuthenticatedUser()` pueda retornar la entidad `User` y asignarla directamente a los campos `creadoPor`/`modificadoPor`. Esto evita una consulta adicional al repositorio en cada operación de auditoría.
   863→
   864→### 12.4 Mapeo DTO Manual (sin MapStruct)
   865→
   866→**Decisión:** El mapeo entre entidades y DTOs se realiza manualmente en cada `ServiceImpl`.
   867→
   868→**Justificación (presumida):** Simplicidad inicial del proyecto, evitar una dependencia adicional.
   869→
   870→**Trade-off:** Genera duplicación significativa de código. Por ejemplo, `toEmpresaResponse()` está duplicado en al menos 4 servicios diferentes (`VehiculoServiceImpl`, `ChoferServiceImpl`, `RecorridoServiceImpl` y posiblemente otros). Una refactorización futura con MapStruct o con mappers compartidos reduciría el código y mejoraría el mantenimiento.
   871→
   872→### 12.5 Sin Migraciones de Base de Datos (ddl-auto=update)
   873→
   874→**Decisión:** Se utiliza `spring.jpa.hibernate.ddl-auto=update` para generar y actualizar el esquema automáticamente.
   875→
   876→**Justificación:** Rapidez en el desarrollo inicial.
   877→
   878→**Trade-off:** Este enfoque es frágil para cambios de esquema en producción (no genera `ALTER TABLE` para renombrar o eliminar columnas). Para producción, se recomienda migrar a Flyway o Liquibase.
   879→
   880→### 12.6 Respuestas DTO Anidadas Completas
   881→
   882→**Decisión:** Los DTOs de respuesta incluyen objetos anidados completos. Por ejemplo, `RecorridoResponse` contiene un `VehiculoResponse` completo, que a su vez contiene `EmpresaResponse`, `MarcaResponse`, etc.
   883→
   884→**Justificación:** Simplifica el consumo del API para el frontend, evitando múltiples llamadas para obtener datos relacionados.
   885→
   886→**Trade-off:** Riesgo de problemas de rendimiento por lazy loading (N+1 queries) y respuestas muy grandes. El setting `spring.jpa.open-in-view=false` ayuda a detectar estos problemas en tiempo de desarrollo.
   887→
   888→### 12.7 Paginación 1-based desde el Cliente
   889→
   890→**Decisión:** Los controladores exponen parámetros de paginación 1-based (page=1 es la primera página) y `PaginationUtils.params()` convierte internamente a 0-based para Spring Data.
   891→
   892→**Justificación:** Más intuitivo para los consumidores del API.
   893→
   894→**Trade-off:** Si el cliente envía `page=0`, `PaginationUtils.params()` lo convierte a `Math.max(0, 0-1) = 0`, lo que es correcto pero podría confundir. La consistencia del API depende de la documentación.
   895→
   896→### 12.8 Sesiones Stateless con JWT
   897→
   898→**Decisión:** La configuración de seguridad establece `SessionCreationPolicy.STATELESS` y no se almacena estado de sesión en el servidor.
   899→
   900→**Justificación:** Facilita la escalabilidad horizontal y es el patrón estándar para APIs REST consumidas por frontends SPA o móviles. El estado se codifica en el propio token JWT.

   931→### 13.3 Bug Crítico en Pruebas
   932→
   933→**11 de 13 archivos de prueba** tienen un error de mocking consistente: el método de prueba `findAllShouldReturnPagedResponses()` mocka `repository.findAll(pageable)`, pero la implementación real del servicio llama a `repository.findAllByActivoTrue(pageable)`. Como Mockito retorna `null` para métodos no mockeados, se produce un `NullPointerException` al invocar `.map()` sobre el resultado `null`.
   934→
   935→**Fix necesario:** Reemplazar `when(repository.findAll(pageable)).thenReturn(page)` con `when(repository.findAllByActivoTrue(pageable)).thenReturn(page)` en los 11 archivos afectados, y actualizar las llamadas `verify()` correspondientes.

   976→## 15. Problemas Conocidos y Mejoras Pendientes
   977→
   978→### 15.1 Problemas Conocidos
   979→
   980→| # | Severidad | Problema | Descripción |
   981→|---|---|---|---|
   982→| 1 | 🔴 Alta | Bug en pruebas unitarias | 11 de 13 archivos de prueba fallan por mock incorrecto (`findAll` vs `findAllByActivoTrue`) |
   983→| 2 | 🟡 Media | JWT secret hardcoded | La clave JWT está en `application.properties` como texto plano. Debería usarse variable de entorno o vault |
   984→| 3 | 🟡 Media | Contraseña admin hardcoded | `admin123` en `DataInitializer.java` es una contraseña por defecto insegura |
   985→| 4 | 🟡 Media | Duplicación de mapeo DTO | `toEmpresaResponse()` y otros mappers están duplicados en múltiples servicios |
   986→| 5 | 🟠 Baja | Sin migraciones DB | `ddl-auto=update` es frágil para producción; no controla cambios de esquema |
   987→| 6 | 🟠 Baja | Riesgo N+1 queries | Respuestas DTO con anidamiento profundo + lazy loading pueden causar problemas de rendimiento |
   988→| 7 | 🟠 Baja | Sin caché | Cada llamada al servicio impacta la base de datos sin capa de caché |
   989→| 8 | 🟠 Baja | Page 0 API inconsistency | Si el cliente envía `page=0`, la conversión 1→0-based da 0 (funciona pero es confuso) |
   990→
   991→### 15.2 Mejoras Recomendadas
   992→
   993→1. **Corregir las 11 pruebas unitarias** — Cambiar el mock de `findAll` a `findAllByActivoTrue`
   994→2. **Introducir MapStruct** — Eliminar duplicación de mapeo DTO, generar mappers en tiempo de compilación
   995→3. **Externalizar credenciales** — Mover JWT secret y contraseña admin a variables de entorno
   996→4. **Adoptar Flyway o Liquibase** — Control versionado del esquema de base de datos para producción
   997→5. **Implementar `@EntityGraph` o FETCH JOIN** — Evitar problemas N+1 en respuestas anidadas
   998→6. **Crear mappers compartidos** — Como paso intermedio antes de MapStruct, extraer mapeos comunes a clases utilitarias
   999→7. **Agregar pruebas de integración** — Al menos para los flujos críticos (recorridos, autenticación)
  1000→8. **Implementar rate limiting** — Proteger los endpoints de autenticación contra ataques de fuerza bruta
